从今天开始，我觉得我已经开始进入生产级的研发阶段。然后今天首先是把昨天做的这个知识工程智能体给分装了一下，但是现在其实还不算是智能体，只是个壳。然后我在分装的时候发现了一个路径问题，然后我现在这会儿正在处理这个路径问题，去分装技术库，就是随着这个。嗯，过程自然而然地去一点一点地去把积木块堆起来，然后呢，因为所有的地方我都有思路，所以说其实无非就是说在进度上稍微的慢一点，我觉得整体的思路其实没有什么太大的问题，然后，就是虽然会有点慢，但是已经感觉慢慢适应

双系统切换过于频繁负担很重。所以我改为了简化流程。在状态上管理更加精细。开源社区的保留文件非常其实非常非常多和细致。然后呢，我今天增加了一个 status 用来去记录当前的状态。然后又加上一个 to do 来记各种待办，这样子的话就把 roadmap 给变得更纯净了，然后呢，更遵循 AI 的使用习惯。然后 Roadmap 就变成了一个小版小的版本的发布目标，然后并且不写具体怎么做。然后呢，这个它作为蓝图性质的东西就会更加清楚，然后呢，To do 就和 open code 的自己的那个代办列表就比较适配，明显感觉到质量会比较高。然后 Status 又比较适合在 review 的时候写，然后阶段性的总结，然后记录当前的状态，这个也是比较好的。然后，产生了一个新的问题是这些活文档本身的维护，就是这是一个不小的难题

然后我在想，就是我自己研发的这个编程的机制之中，我觉得我要大量地去应用这些特殊文件来去规范整个系统的效果。然后呢，就是说我大概计划是一个 owner 一个 reviewer，这个 owner 主要负责执行，然后呢，这个 reviewer 主要负责评审和维护这些特殊文件。然后把整个系统给简化成就是大量的通过这个社区规范来去内置状态，就让这个代码质量本身提高的方式来去避免混乱和同步状态

然后最好其实是能够把文件系统的变化给监听上来，然后把这个信息作为上下文注入到两个系统里边，我觉得这会是一个比较好的办法。但是呢，就会担心说如果过于频繁的话可能也会有问题，所以说，反正这个问题还挺不好处理的对，想到了一个折中的办法，就是让这个状态先存下来，然后等他用的时候再自然注入，这样就可以避免说过度过分的主动触发，就主动触发这个，除了用户输入信息之外，其他的还是要比较小心的，要避免他费偷客。然后就是，整个系统内部的这种 token 的用量，本地的 token 的用量得更加的透明化，就是能够统计，能够让用户看到构成是什么样子，然后大概知道这些 token 带来了什么效果。我觉得这这也是一个很重要的点，就也给优化提供了更加方便的那个空间

然后我刚才让他自己写 ReAct 循环。就我的考虑是，既然这个已经是一个比较标准的范式了，那么理论上来讲的话，我就先把这个循环给内置进去，然后再考虑其他的就可以了。就我觉得这可能是一个提高效率的办法，就是现在的情况是我在这个系统里面堆了一大堆的那个功能，然后呢，大概率是用不起来的。然后呢，我现在要做的事情就是不断的压缩，把所有可能有用的功能都先给压进去，然后再考虑后面怎么去处理

就是说整个系统我们要允许大量的 breaking change, 然后反正就是在我本地，然后不断的用，就通过这种方式来提高它的效率。
