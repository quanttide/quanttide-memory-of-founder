混合工程真的是不容易，又搞了一晚上才搞出来，终于成功发了一个。但是其实没有完全的成功，就还是有很多小问题。然后我打算先放着，让他先勉强能用再说。反正现在目前处在一种能上传能下载的状态就行了。然后能用能用就是可能不是太好用。然后，接下来就开始逐渐地把这个项目从 Python 到 rust 的迁移。因为从实际的表现来看的话，就是 Python 的稳定就是这种混合编程不稳定性还是很多，就是那既然就彻底一点，把它彻底往 rust 的这个方向去转是最合适的。

就从各种机制上来看的话，rust 本身支持的机制是比较符合现代的规工程规范，所以这个会让正式上线减少很多麻烦，Python 的话，倒不是我不懂，而是 AI 不懂，反复的调教它会浪费大量的时间，所以直接换工具链可能效率会高一点。就是这个地方从混合工程逐渐迁移到一个 rust 的项目需要一些时间，感觉这个是一个难点

然后，这种先实验代码再开发的方法真的非常非常好用，就是它极大程度地减少了这个工程上的难点，就是到集成的时候就只是无脑地在在在处理各种麻烦事，就是感觉到这个研发的流程被彻底地平滑了就感觉这个方向对了，就是说只有当功能全部完善的时候才应该开始上生产，对我觉得这是很重要的一个标志

而且明显有一种这个工具造对了的感觉，就是 AI 在反复地用这个工具来解决问题，就发现我我而且我还发现了一个点，就是说 AI 是很重视反馈的，就是它用了之后觉得这个工具好用，他就会一直用它。所以这本身就是一个标准，就是他也是一个用户，对你像之前 release 那个命令他就用得不熟练就不爱用，因为他自己也能搞对你，就不像这个检测检测这种检测，它就属于用得比较相对来讲会好一点的。我觉得当然也有一种可能是在这个工程语境之下就是。他对这个比较熟悉一点，就是如果换一个领域，他可能用的就不熟练，这也是一个原因

但是明显感觉到这个工具的水平开始提高了，我觉得这是很重要的一点。对，就是我感觉到了我的水平在提高。然后本来是想发一个小版本的，但是更新太大了，发还是发一个 minor 次版本比较合适一点。然后如果下一个版本要重构的话，再再接着升版本号就行，感觉还是版本号升的要快一点。对，要不然的话，进度提不起来，对，就基本上 API 初步稳定就可以发了。就之后如果要再有变化，再升版本号就行，也不用太害怕升版本号这件事情

就不过今天这个情况呢，其实用预发布效果会好一点，但是现在反正也是那个，早期版本就无所谓了，发了就发了，之后的话看需要可以慢慢地加预发布，主要是加预发布会把流程变复杂，暂时不想折腾这个东西
