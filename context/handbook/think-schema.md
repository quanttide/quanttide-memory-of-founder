# 图式质量标准

从实践中总结的图式（Schema）定义规范。

## 高质量图式的条件

| # | 条件 | 说明 | 例子 |
|---|------|------|------|
| 1 | **触发-响应结构完整** | 明确在什么场景下使用（trigger），解决什么问题（description） | "适用于用户需求模糊、设计逻辑反直觉...场景；在任务明确或用户焦虑时应避免" |
| 2 | **可迁移性** | 脱离原文语境仍成立，能复用到不同场景 | "讲故事传递意图"不依赖当日日记，可迁移到任何产品设计场景 |
| 3 | **有边界条件** | 明确"什么时候该用、什么时候不该用"，不只有正面描述 | trigger 字段同时给出适用场景和避免场景 |
| 4 | **命名精炼** | 标题本身就是一个完整的概念，无需额外解释 | "层次化心智模型"、"讲故事传递意图" |
| 5 | **核心思想一句话说清** | description 凝练到一句话，不啰嗦、不堆砌 | "过去定义的心智模型过于粗糙，颗粒度不够导致无法用于计算和推理" |

## 需要避免的情况

| ❌ | 情况 | 判别标准 | 例子 |
|----|------|----------|------|
| ❌ | **一次性想法** | 只是单次洞察或假设，无法脱离原文复现 | "流转创新实验产出"——实际是个意图，不是可复用的认知模式 |
| ❌ | **缺少触发条件** | 只说"是什么"不说"什么时候用" | 只有 description 没有 trigger 的图式不完整 |
| ❌ | **颗粒度过粗** | 描述泛泛，无法指导具体行为 | "要提高认知"——太宽泛，不形成图式 |
| ❌ | **原文绑定** | 离开了日记原文就读不懂 | 如果需要在 description 里引用日记原文才能说清，说明没提炼够 |

## 格式

```yaml
title: 图式名称（精炼的完整概念）
description: 核心思想（一句话说清）
trigger: 适用场景 + 应避免的场景（有边界条件）
```
